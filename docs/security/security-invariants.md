# Security invariants

Status: **Proposed (Phase 0).** Not owner-approved and not independently reviewed.

These are properties every Ruvee component must keep. Each one names how it is enforced and how a
test proves it. A change that would break an invariant needs an ADR and an update here, not a
code comment. Specifications that rely on an invariant link to it by id.

"Client" means any enrolled Ruvee app: web, extension or mobile.

## Confidentiality

| ID     | Invariant                                                                                                                                                                  | Enforced by                                                                                                                                                                                                                                | Verified by                                                                                                                                                                                                                                                                                                                                                                           |
| ------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| INV-01 | The server never receives the master password, `PwK`, `AUK`, `SK`, `AK`, `VK`, any `IK`, `RK`, `RWK` or item plaintext.                                                    | API request schemas accept only opaque byte fields (envelopes, records, OPAQUE messages, hashes) and documented metadata ([api-design.md](../architecture/api-design.md)). The API package has no dependency on the client crypto package. | Contract tests that list every request field and its type. A capture test runs the end-to-end flows with known synthetic secrets and asserts none of their bytes, hex or base64 forms appear in any request body, header, URL or server log. A dependency-boundary lint for `apps/api`.                                                                                               |
| INV-10 | Server-visible plaintext is limited to the list in [threat-model.md §4](threat-model.md#4-what-the-server-can-see).                                                        | Database columns are documented with a confidentiality class ([database-design.md](../architecture/database-design.md)). A new plaintext column requires updating that list.                                                               | A schema review checklist item. A migration test fails on any column missing from the documented column list.                                                                                                                                                                                                                                                                         |
| INV-16 | No client persists vault plaintext or unwrapped keys. Local stores hold only encrypted envelopes and records, plus the exceptions in INV-17.                               | Local storage modules accept only envelope bytes. Plaintext types cannot be passed to storage APIs.                                                                                                                                        | A test that writes a vault, locks, then scans every byte of IndexedDB or the app sandbox for synthetic secret markers.                                                                                                                                                                                                                                                                |
| INV-17 | The Secret Key, which is stored on each device without password protection, never decrypts anything on its own. Decryption needs `SK` together with the password, or `RK`. | Key hierarchy ([cryptographic-design.md §3](cryptographic-design.md#3-secrets-and-keys)).                                                                                                                                                  | A vector test showing `AUK` changes with the password for a fixed `SK`. A test that no envelope purpose is keyed by `SK` or a value derived from `SK` alone.                                                                                                                                                                                                                          |
| INV-12 | No secret, token, password or plaintext appears in logs, URLs, error responses, analytics or crash reports.                                                                | Allow-listed log serializers; secrets only in bodies, cookies or `Authorization` headers; error filter with fixed messages ([api-design.md](../architecture/api-design.md#logging)). No third-party telemetry.                             | Existing Phase 1 logger tests, extended per endpoint. Since P2-05, [`logging.spec.ts`](../../apps/api/test/logging.spec.ts) sends a synthetic secret in paths, query strings, headers, cookies, bodies and exception messages and checks every captured log line and response. The INV-01 capture test also scans logs. A lint rule against query parameters on authenticated routes. |
| INV-18 | No administrator, server key, escrow or support process can decrypt a vault. Administrative reset destroys data; it never recovers it.                                     | There is no server-held decryption key in the design. The admin CLI has no read access to decrypted data, because none exists on the server.                                                                                               | Design review. A test that the admin reset command removes all vault and key-wrap rows.                                                                                                                                                                                                                                                                                               |

## Cryptographic correctness

| ID     | Invariant                                                                                                                                                            | Enforced by                                                                                                                                   | Verified by                                                                                                                                                                         |
| ------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| INV-02 | Every symmetric encryption produces a format-version-1 envelope with a fresh 24-byte nonce from the CSPRNG. No production code path accepts a caller-supplied nonce. | A single `seal()` function in `packages/crypto`; the nonce parameter exists only on a separate test-only export.                              | A uniqueness test (two encryptions produce different nonces). A lint or import rule banning the test-only export outside tests and the vector runner.                               |
| INV-03 | Every decryption states the expected purpose, key id and context. The AAD is rebuilt from those expectations, never read from the envelope or the server.            | The `open()` signature requires a typed expected-context argument per purpose.                                                                | Negative vectors: wrong item, revision, `seq`, vault, purpose or key id each fail ([cryptographic-design.md §8](cryptographic-design.md#8-test-vectors-and-interoperability-plan)). |
| INV-04 | Decryption fails closed. There is no partial plaintext, no fallback to another format version, key or algorithm, and no silent skip.                                 | Typed errors; callers must handle each error type.                                                                                            | Fuzz tests on the decoder. Tests that every error type surfaces to the UI or sync layer.                                                                                            |
| INV-05 | Clients derive password keys only with a known profile id at or above the floor (profile 1). Raw KDF parameters are never accepted from the server.                  | Profile registry compiled into the client.                                                                                                    | A test that unknown or lower profile ids from the server fail before any derivation.                                                                                                |
| INV-22 | Cryptographic dependencies are pinned to exact versions, and every update is reviewed against these documents before merging.                                        | Exact versions in `package.json`, lockfile, pnpm minimum-release-age, and a CODEOWNERS-style review rule for `packages/crypto` and auth code. | A CI check that crypto dependencies use exact versions. The release checklist.                                                                                                      |

## Authentication and authorization

| ID     | Invariant                                                                                                                                                                                                                       | Enforced by                                                                                                                                                                                                         | Verified by                                                                                                                                       |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| INV-06 | A server session alone never grants decryption. A new device gains `SK` only through pairing with an unlocked enrolled device, or through the Recovery Key.                                                                     | Device enrollment protocol ([device-enrollment.md](device-enrollment.md)). The server stores nothing that decrypts with a session alone.                                                                            | An end-to-end test: log in on a fresh browser and confirm it cannot unlock without pairing. A test that the pairing reply fails with a wrong MAC. |
| INV-11 | Server authentication and vault decryption are independent. No vault key is derived from OPAQUE outputs, and no authentication secret is derived from vault keys. The only exception is `RAK`, derived from `RK`.               | [ADR-0004](../adr/0004-opaque-authentication.md); code review of `packages/crypto` imports.                                                                                                                         | A test that `export_key` is not used. Vector review.                                                                                              |
| INV-13 | Session and refresh tokens are 256-bit random values, stored only as SHA-256 hashes. Web session cookies are `__Host-` prefixed, `HttpOnly`, `Secure` and `SameSite=Strict`.                                                    | Sessions module ([authentication.md](authentication.md#5-sessions)).                                                                                                                                                | Unit tests on token creation and storage. Cookie attribute tests in HTTP tests.                                                                   |
| INV-14 | Password change, recovery-key rotation, device revocation, key rotation, vault reset and plaintext export need a step-up authentication completed within the last 5 minutes.                                                    | A step-up guard on those endpoints.                                                                                                                                                                                 | HTTP tests for each guarded endpoint with a stale or missing step-up.                                                                             |
| INV-20 | Account registration is closed except through a single-use, expiring, hashed bootstrap token. After the first account exists, registration is disabled.                                                                         | Bootstrap module ([authentication.md](authentication.md#3-account-bootstrap)).                                                                                                                                      | HTTP tests for reuse, expiry, and registration after the first account.                                                                           |
| INV-21 | The OPAQUE server secret is never stored in PostgreSQL or database backups, never logged and never returned by an API.                                                                                                          | Loaded from a file or secret at startup; configuration validation rejects it in `DATABASE_URL`-adjacent settings.                                                                                                   | A configuration test, a log-scan test, and a backup script check (Phase 7 and later).                                                             |
| INV-23 | Server-side protocol state is single-use: an OPAQUE login or reauth state, a pairing (one request, one approval), a recovery session's completion, and a bootstrap token are each consumed atomically and never accepted twice. | Delete-and-return (or a conditional update) in one transaction before the state is used. The OPAQUE library itself accepts a replayed login state ([architecture-validation.md](architecture-validation.md), V-04). | HTTP tests that replay each one, including two concurrent requests with the same state.                                                           |

## Integrity and sync

| ID     | Invariant                                                                                                                                                                                                          | Enforced by                                                                                                                               | Verified by                                                                                                           |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| INV-07 | A client applies remote vault state only after verifying the manifest: it decrypts, its `seq` is at least the local checkpoint, the hash chain connects to the checkpoint, and `items_digest` matches the records. | Sync engine ([sync-protocol.md](../architecture/sync-protocol.md#rollback-and-deletion-detection)).                                       | Simulated malicious-server tests: replayed records, dropped items, an older manifest, a forked chain, a wrong digest. |
| INV-08 | No concurrent change is overwritten silently. A remote change to an item with pending local edits always produces an explicit conflict.                                                                            | Revision preconditions on the server; conflict handling in the client ([sync-protocol.md](../architecture/sync-protocol.md#6-conflicts)). | Two-offline-devices tests for edit/edit and edit/delete.                                                              |
| INV-09 | A client never accepts a keyset version lower than the highest it has seen.                                                                                                                                        | Local checkpoint of `keyset_version`.                                                                                                     | A malicious-server test that serves an older keyset.                                                                  |

## Client behavior

| ID     | Invariant                                                                                                                                                                    | Enforced by                                                                                                 | Verified by                                                                                                                                                     |
| ------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| INV-15 | Locking, logging out or session expiry drops all references to keys and decrypted items. Key buffers are zeroed where the runtime allows, and sensitive UI state is cleared. | A vault lock manager in each client ([sync-protocol.md](../architecture/sync-protocol.md#memory-and-lock)). | Tests that after lock no decrypted item is reachable from app state, and that `memzero` was called on key buffers. Tests are limited by what JavaScript allows. |
| INV-19 | Extension content scripts never receive keys or the vault. They receive at most the single credential the user chose to fill, for the verified origin.                       | Phase 5 extension architecture.                                                                             | Phase 5 message-spoofing and origin tests.                                                                                                                      |

## Changes after architecture validation

Status remains **Proposed**. On 2026-10-22, INV-23 (single-use server-side protocol state) was
added, because `@serenity-kit/opaque` accepts a replayed server login state
([architecture-validation.md](architecture-validation.md), V-04 and V-09).

## Changes after P2-05 (API contracts and conventions)

Status remains **Proposed**. On 2026-10-23 INV-12's tests were extended with the sentinel
log-scan test. No invariant changed.

## Changes after P2-03 (`packages/crypto`)

Status remains **Proposed**. On 2026-10-24 `packages/crypto` added the first tests for INV-02
(nonce uniqueness; the fixed-nonce module is test-only, enforced by lint and a test), INV-03
(negative cases for every context field of the two implemented purposes), INV-04 (decoder
fuzzing with typed errors only), INV-05 (unknown and reserved profiles fail before any library
call), INV-17 (`AUK` changes with the password for a fixed `SK`; no purpose is keyed by `SK`) and
INV-22 (exact pins, one locked `libsodium-sumo`, the runtime library version). They cover only the
implemented purposes. No invariant changed.
