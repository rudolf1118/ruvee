# Research sources for security-critical choices

Status: **Proposed.** Evidence gathered by the Phase 0 agent; not owner-approved and not
independently reviewed.

All sources were checked on **2026-10-22** unless stated otherwise. Package metadata came from
the npm registry API (`https://registry.npmjs.org/<package>`) and crates.io API on that date.
Where a fact was verified by running code, the method is stated.

Each entry says what the source establishes and, just as important, what it does not establish.
A standardized algorithm is not the same as an audited implementation, and an audit of an older
version does not cover the version Ruvee would ship.

## Standards

| Topic             | Source                                                                                                                 | What it establishes                                                                                                                                                                                                                                     |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| OPAQUE            | [RFC 9807](https://www.rfc-editor.org/rfc/rfc9807.html) (Informational, July 2025)                                     | Byte-level OPAQUE spec. Server never sees the password. Clients MUST NOT use `export_key` before authenticating the server (Section 6). Section 10.9: fake responses for unknown users; registration is an enumeration oracle and must be rate-limited. |
| Argon2            | [RFC 9106](https://www.rfc-editor.org/rfc/rfc9106.html) (Section 4)                                                    | First recommended: Argon2id t=1, p=4, m=2 GiB. Second recommended (memory-constrained): t=3, p=4, m=64 MiB, 128-bit salt, 256-bit tag.                                                                                                                  |
| Password hashing  | [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) | Minimum Argon2id configurations with p=1, e.g. m=19 MiB t=2, or m=46 MiB t=1. These are server-side minimums, not targets for client-side vault keys.                                                                                                   |
| XChaCha20         | [draft-irtf-cfrg-xchacha-03](https://datatracker.ietf.org/doc/draft-irtf-cfrg-xchacha/)                                | **Expired draft (rev 03, expired 2020-07-13); not an RFC.** The construction is widely implemented (libsodium, Go `x/crypto`, PyCryptodome) and has published test vectors, but it has no IETF standard status.                                         |
| WebCrypto storage | [W3C Web Cryptography Level 2, "Key Storage"](https://www.w3.org/TR/webcrypto-2/)                                      | Non-extractable `CryptoKey` objects can be stored in IndexedDB. This prevents export by script only; it gives no protection against XSS (which can use the key) or copying of the browser profile.                                                      |

## Platform constraints

| Topic                             | Source                                                                                                                                                           | What it establishes                                                                                                                                                                                                            |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| MV3 extension CSP and WebAssembly | [Chrome: Manifest content security policy](https://developer.chrome.com/docs/extensions/reference/manifest/content-security-policy)                              | Extension pages and the service worker can run WASM with `script-src 'self' 'wasm-unsafe-eval'`. `'unsafe-eval'` and remote scripts are rejected.                                                                              |
| MV3 service-worker lifecycle      | [Chrome: Extension service worker lifecycle](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle)                            | Chrome terminates the worker after 30 s of inactivity; globals are lost. Unlocked state must not rely on worker globals.                                                                                                       |
| Extension storage                 | [Chrome: `chrome.storage` API](https://developer.chrome.com/docs/extensions/reference/api/storage)                                                               | `storage.session` is memory-only, cleared on browser restart or extension reload, and not exposed to content scripts by default. `storage.local` **is** exposed to content scripts by default unless `setAccessLevel` is used. |
| React Native and WebAssembly      | [React Native 0.84 release notes](https://reactnative.dev/blog/2026/02/11/react-native-0.84); [Hermes issue #429](https://github.com/facebook/hermes/issues/429) | Hermes V1 is the default from RN 0.84 (Feb 2026). Native WebAssembly support in Hermes is new; compatibility of wasm-bindgen packages such as `@serenity-kit/opaque` on Hermes is **unverified**.                              |

## Prior art consulted

| Design                              | Source                                                                                                                      | Relevance                                                                                                                                                                                                            |

| 1Password two-secret key derivation | [1Password Security Design White Paper, "A deeper look at keys"](https://agilebits.github.io/security-design/deepKeys.html) | Combines the account password with a 128-bit device-held Secret Key, so data stored on the server cannot be used to crack the password. Ruvee's proposed Secret Key follows the same idea with different primitives. |

## Not researched or unresolved

- **Argon2id timing on real target devices.** Only Node 24 on an Apple Silicon Mac was measured.
  Browser main thread, Web Worker, MV3 service worker, older Android phones and iOS devices are
  unmeasured. See [risk R-03](risk-register.md).
- **libsodium.js inside the MV3 service worker.** The CSP allows WASM, but loading the sumo
  build in a module service worker has not been tried.
- **OPAQUE on React Native.** No maintained binding of `opaque-ke` 4.x exists for React Native.
  Whether to fork `react-native-opaque`, write a UniFFI binding, or use Hermes WebAssembly is
  undecided. See [open decision D-05](../architecture/open-decisions.md).
- **Next.js 16 strict CSP.** Nonce-based CSP with the App Router, and its interaction with
  static rendering, has not been verified against the current release.
- **iOS Keychain, Secure Enclave and Android Keystore details** for biometric unlock were not
  researched in Phase 0. They are Phase 6 concerns, and the crypto design only reserves a slot for
  a device-bound wrapping key.
