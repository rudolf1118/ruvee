# Crypto primitive validation harness (P2-01)

This harness checks the **candidate primitive libraries** (libsodium.js, with `@noble/*` as a
second implementation) against published test vectors, against each other, and against the
library behavior Ruvee's proposed design relies on. It runs in Node and in Chromium, Firefox and
WebKit through Playwright, both on the page and in a dedicated Web Worker.

What it is not:

- **Not Ruvee's cryptographic format.** It builds no envelope, no key hierarchy and no
  application encryption API, and it produces no authoritative Ruvee vectors. Those wait for
  P2-03 and a format review.
- **Not an audit.** It is a self-built regression check. Passing it says the pinned libraries
  produce the published bytes and behave as recorded here. It says nothing about side channels,
  memory hygiene, or whether Ruvee's protocol is sound.
- **Not production code.** Nothing in `apps/*` or `packages/*` imports it. It is outside the
  pnpm workspace and has its own `package-lock.json`.

**All inputs are synthetic.** Keys, passwords, messages and salts are either taken from the
published vector files or generated by a fixed, library-independent generator
(`synthetic(label, length)` in `src/bytes.mjs`). No real secret is used anywhere.

Scope approved by the owner as decision D-25. That approval covers this harness only. The
cryptographic protocol, pairing, authentication, recovery, database schema and every other
decision in [open-decisions.md](../../docs/architecture/open-decisions.md) remain **Proposed**.

### How independent the cross-checks are

noble and libsodium are separate code bases in different languages, so agreement between them
rules out most implementation bugs. It is **not independent proof of correctness**, for these
reasons:

- **Shared reference code.** libsodium's Argon2 is derived from the Argon2 reference
  implementation (P-H-C/phc-winner-argon2), which also produced the RFC 9106 and `test.c`
  vectors. libsodium's BLAKE2b is derived from the BLAKE2 reference code that produced
  `blake2b-kat.txt`. libsodium's Poly1305 and noble's Poly1305 are both described as based on
  poly1305-donna.
- **Shared vectors.** The XChaCha draft lists libsodium as an implementation and does not say
  how its vectors were generated. Wycheproof test 1 is the draft's vector. noble's own test suite
  may use vectors produced with libsodium (not verified here).
- **Shared specifications.** A mistake in a specification would be reproduced by both.
- **Audit coverage.** noble's audits do not cover its Argon2 implementation. Here noble Argon2id
  is trusted only to the extent that it reproduces RFC 9106 §5.3 and the eight reference
  `test.c` vectors.

## Test categories

The four categories are kept separate in code (`src/checks/*.mjs`), in the results and in this
README. Every check states where its expected value comes from (`expectedFrom`).

### 1. Published known-answer tests (17 checks)

Expected bytes are **parsed at run time from the published files** in `vectors/`, after each
file's SHA-256 has been verified. None comes from the implementation under test. Each vector
runs through libsodium and, separately, through noble (which validates noble as an oracle for
category 2).

| Argon2id                    | Argon2 reference `test.c`, the 8 Argon2id `hashtest()` cases: version 0x13, p = 1 or 2, 8-byte salt, no secret or associated data; raw tag and encoded string | Through `crypto_pwhash_str_verify` | Yes   |
| HChaCha20                   | draft-irtf-cfrg-xchacha-03 §2.2.1                                                                                                                             | `crypto_core_hchacha20`            | Yes   |
| XChaCha20-Poly1305 with AAD | draft-irtf-cfrg-xchacha-03 §A.3.1 (12-byte AAD)                                                                                                               | Encrypt and decrypt                | Yes   |
| XChaCha20-Poly1305          | Wycheproof `xchacha20_poly1305_test.json`, all 315 tests: 246 valid, 69 invalid (including 9 invalid nonce sizes)                                             | Yes                                | Yes   |
| BLAKE2b-512                 | RFC 7693 Appendix A, `"abc"`                                                                                                                                  | `crypto_generichash`               | Yes   |

**Argon2id parameter mapping.** libsodium's `crypto_pwhash(outlen, password, salt, opslimit,
memlimit, crypto_pwhash_ALG_ARGON2ID13)` is Argon2id version 0x13 (19) with t = `opslimit`,
m = `memlimit / 1024` KiB (rounded down), p = 1, a 16-byte salt and no secret or associated data.
The harness confirms this mapping three ways: libsodium's own encoded string
(`LB-ARGON2-ENCODED-PARAMETERS`), agreement with noble at those parameters
(`CROSS-ARGON2ID-PWHASH`), and the published vectors through noble.

**BLAKE2b modes covered.** Unkeyed and keyed (key = digest length) at 20, 32, 48 and 64 bytes
(Appendix E). Keyed with a 64-byte key at 64 bytes (reference KAT). BLAKE2b-512 unkeyed
(Appendix A). Keyed BLAKE2b-256 with a 16-byte key, and salt plus personalization (used by
`crypto_kdf`), have **no published vectors** and are covered by category 2 only.

### 3. Library behavior and boundary checks (13 checks, plus one browser-only check)

These record what the library does with tampered, malformed and out-of-range input. Each check
carries an enforcement label, so the results never imply that libsodium enforces something that
only a caller can:

- **Enforced by the library**: the library rejects the input itself.
- **Not enforced by the library**: the library accepts it. A caller-side check would be needed.
  Several of these checks are tripwires that fail if a future release starts enforcing, which is
  the signal to revisit the finding.

| Check                                           | Enforcement  | What it shows                                                                                                                                                                                                      |
| ----------------------------------------------- | ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `LB-AEAD-TAMPER-REJECTED`                       | Library      | A bit flipped in the ciphertext, tag, nonce or AAD, or a wrong key, is rejected without returning plaintext (14 cases). The error text is recorded, not asserted.                                                  |
| `LB-AEAD-TRUNCATED-MALFORMED`                   | Library      | Truncated, extended, empty and malformed ciphertexts are rejected. Shorter than the tag gives `TypeError`; an authentication failure gives `Error`. A caller must not expose that difference.                      |
| `LB-AEAD-KEY-NONCE-LENGTHS`                     | Library      | Keys other than 32 bytes and nonces other than 24 bytes are rejected by encrypt and decrypt.                                                                                                                       |
| `LB-INPUT-TYPE-COERCION`                        | Not enforced | Strings are accepted as keys, messages and AAD and silently UTF-8 encoded; a 32-character string is accepted as a 32-byte key. Buffers are accepted. Arrays, ArrayBuffers and other typed arrays are rejected.     |
| `LB-BLAKE2B-KEY-LENGTH`                         | Not enforced | **The BLAKE2b key-length discrepancy:** keys of 1 to 15 bytes are accepted although `crypto_generichash_KEYBYTES_MIN` is 16. The output is still correct BLAKE2b (it matches noble). 65-byte keys are rejected.    |
| `LB-BLAKE2B-OUTPUT-LENGTH`                      | Not enforced | Outputs of 1 to 15 bytes are accepted although `crypto_generichash_BYTES_MIN` is 16; 0 and 65 are rejected.                                                                                                        |
| `LB-KDF-ARGUMENTS`                              | Mixed        | Wrong context or key lengths and out-of-range ids are rejected. An 8-byte non-ASCII context is accepted. Numeric ids stop at 2³¹ − 1; bigint ids reach 2⁶⁴ − 1.                                                    |
| `LB-KDF-SUBKEY-LENGTH-STALE-MEMORY`             | Not enforced | **Finding V-15.** Subkey lengths 15 and 65 are not rejected; the result is uninitialized WebAssembly memory, including a previous derivation's subkey made with a different key (see below).                       |
| `LB-ARGON2-INVALID-REJECTED-WITHOUT-ALLOCATION` | Library      | 22 invalid parameter sets are rejected and the library stays usable. The wrapper's type checks never grow the heap. Out-of-range values that reach the C library grow it by at most 1 MiB (832 KiB observed once). |
| `LB-ARGON2-SILENT-ADJUSTMENTS`                  | Not enforced | `memlimit` is silently rounded down to whole KiB; outputs above 64 bytes are accepted; there is no memory ceiling below the WebAssembly limit. `ALG_DEFAULT` is Argon2id v1.3.                                     |
| `LB-ARGON2-ENCODED-PARAMETERS`                  | Library      | libsodium reports its own mapping: `$argon2id$v=19$m=<memlimit/1024>,t=<opslimit>,p=1$`.                                                                                                                           |
| `LB-CONSTANTS`                                  | Not enforced | Constants above 2³¹ − 1 read as negative numbers (`crypto_pwhash_MEMLIMIT_MAX`, `OPSLIMIT_MAX`, `BYTES_MAX`, `PASSWD_MAX`). The sizes Ruvee relies on have their documented values.                                |
| `LB-STRING-ENCODING`                            | Not enforced | Strings are encoded without normalization (NFC and NFD differ), and a lone surrogate collides with U+FFFD.                                                                                                         |
| `ENV-WASM-CSP-REQUIRED` (browsers only)         | Browser      | Under a CSP without `'wasm-unsafe-eval'`, libsodium fails to initialise, on the page and in the worker. With it (and without `'unsafe-eval'`), every check passes.                                                 |

The heap measurements read `sodium.libsodium.HEAPU8`, an undocumented internal of the build.

### 4. Proposed Ruvee input-validation rules (3 checks)

**These are proposals, not approved protocol requirements.** `src/proposed-rules.mjs` contains
test-local reference predicates for rules suggested in the Phase 0 design. They are not an API
and nothing imports them. The checks show that each predicate rejects the inputs category 3
shows the library accepts, **before any library call** (a recording proxy counts the calls), and
leaves valid results unchanged. Any protection here comes from the harness predicate, not from
libsodium.

| Check                      | Proposal                                     | Rule                                                                                                                                                                                                                                            |
| -------------------------- | -------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `PR-PASSWORD-INPUT`        | D-20, cryptographic-design §3.1, V-05        | Reject non-strings and strings that are not well formed (lone surrogates), apply NFC, require 1 to 4,096 UTF-8 bytes after NFC. Covers composition, compatibility characters left alone, composition exclusions, and NFC growth past the limit. |
| `PR-KEY-AND-LENGTH-GUARDS` | cryptographic-design §2 and §3.3, V-12, V-15 | `Uint8Array` only; MAC keys of 16 or 32 bytes; KDF keys of 32 bytes; 8 printable-ASCII context bytes; subkey length exactly 32.                                                                                                                 |
| `PR-KDF-PROFILE-REGISTRY`  | cryptographic-design §3.2, D-03              | Argon2id parameters come only from the profile registry (profile 1: 64 MiB, t = 3, p = 1, 32 bytes; profile 2 reserved). Unknown, reserved, raw and excessive parameters are rejected.                                                          |

The Argon2id call is stubbed in these checks, so a permissive rule can never trigger a large
allocation.

## Finding V-15: `crypto_kdf_derive_from_key` returns stale memory

In libsodium.js 0.8.4, `crypto_kdf_derive_from_key(subkey_len, …)` with `subkey_len` outside
16..64 does not throw. The C function returns an error, the wrapper ignores the return code, and
the caller receives uninitialized WebAssembly heap memory. In the harness, a 65-byte request made
with key B returns, as its first 64 bytes, the subkey previously derived with key A. During
development the same call also returned plaintext bytes from an earlier AEAD call.

Upstream: [jedisct1/libsodium.js#370](https://github.com/jedisct1/libsodium.js/issues/370)
(closed). Fixed on the master branch by commit `86ea6ed` ("Check output of
crypto_kdf_derive_from_key", 2026-04-29). **Not in any npm release** as of 2026-10-22.

Consequence for Ruvee (proposed): the subkey length must be a constant 32 checked before the call.
`LB-KDF-SUBKEY-LENGTH-STALE-MEMORY` fails when a pinned release fixes this.

## Negative controls

A check that cannot fail proves nothing. After the suite, `src/negative-controls.mjs` injects
faults and requires **the named target check to fail** for each one (78 controls, all detected
in every environment):

- **Wrong expected outputs (37).** Every expected field of every known-answer check (for vector
  lists, the fields of the last entry) is altered by one bit, one character or a negated
  validity flag.
- **Faulty libraries (28).** A proxy replaces one library function: an AEAD that ignores the tag
  or accepts bad lengths; noble BLAKE2b that drops salt and personalization; a KDF that uses the
  wrong id; BLAKE2b or Argon2id outputs with one flipped bit; a verifier that always fails; a
  library that fixes V-15 or enforces the BLAKE2b key minimum (tripwires); an Argon2id that grows
  the heap on rejection; a library that normalizes strings; rules that are permissive or validate
  after the library call.
- **Source integrity (9).** One corrupted byte in each vector file, a missing file, and a malformed
  manifest hash.
- **Completeness (4).** A missing, skipped, duplicated or unknown check result.

In addition, three mutations were made by hand on 2026-10-22, each confirmed to fail the run in
Node (and the second also in Chromium page and worker), then reverted and confirmed byte-identical
by SHA-256: one hex digit in `vectors/blake2b-kat.txt`, the comparison against the RFC 9106 tag
in `KAT-ARGON2ID-RFC9106-NOBLE`, and the password length limit in the proposed rule.

## Commands

Requires Node 24 (the repository's `.nvmrc`). Run from `tools/crypto-validation/`.

```sh
npm ci                                  # exact versions from package-lock.json; install scripts disabled
npm run test:node                       # Node: checks and negative controls; writes results/node.json
npm run install:browsers                # Playwright's Chromium, Firefox and WebKit builds
npm run test:browsers                   # bundle, then all three engines, page and worker; writes results/browsers.json
```

On Linux CI, `npm run install:browsers -- --with-deps` also installs system libraries. It needs
root and changes the machine's packages, so don't use it on a workstation.

Options for `test:browsers`:

- `BROWSERS=chromium,firefox,webkit` (default). Add `chrome` to also run installed Google Chrome.
  Leaving out any of the three default engines **fails the run** and names what was not run.
- `RUN_TIMEOUT_MS` (default 600000) per page or worker run.

Every runner exits non-zero on any failed check, missing result, ineffective negative control,
version mismatch, vector hash mismatch, or browser that fails to launch. Nothing is skipped.

CI: the `crypto-validation` job in `.github/workflows/ci.yml` runs these four commands on
`ubuntu-latest` and uploads `results/` as an artifact.

## Bounds

- Argon2id memory is capped at 64 MiB (`MAX_KDF_MEMORY_KIB = 65536`) for any case the harness
  checks run. The separate calibration benchmark goes up to 256 MiB (profile 2), one derivation
  at a time. Engines, contexts and runs are sequential, so only one heavy derivation is in flight.
- Excluded for memory: the reference `test.c` case with m = 2¹⁸ KiB (256 MiB).
- Excluded for time: RFC 7748's 1,000,000-iteration X25519 result (1 and 1,000 are run).
- The 1 GiB `memlimit` acceptance noted in `LB-ARGON2-SILENT-ADJUSTMENTS` was observed once
  during development and is not run.

## Gaps and limitations

Coverage gaps (none blocks this milestone):

- **Safari, phones and older laptops** are not covered. Playwright WebKit is not Safari, and
  Playwright Firefox is a patched build, not stock Firefox.
- **React Native** (`react-native-libsodium`, Hermes) is not covered (Phase 6).
- **The MV3 extension service worker and offscreen document** are not covered here (Phase 5).
  The architecture spike ran an earlier version of these checks there.
- **Argon2id through libsodium against a published vector:** RFC 9106 §5.3 needs p = 4, a secret
  and associated data, which `crypto_pwhash` cannot take. The reference vectors use 8-byte salts,
  so they run through `crypto_pwhash_str_verify` rather than raw `crypto_pwhash`. Raw
  `crypto_pwhash` with 16-byte salts is covered only by agreement with noble.
- **No published vectors** exist for keyed BLAKE2b-256 with a 16-byte key, BLAKE2b with salt and
  personalization, `crypto_kdf`, sealed boxes or padding. They are cross-checked only.
- **Unicode:** NFC behavior is checked on hand-picked cases, not on `NormalizationTest.txt`, and
  the Unicode version of each engine is not pinned or compared.
- Not measured: side channels, constant-time behavior, memory wiping, peak memory, and
  performance (P2-02).
- Not covered: SHA-256 (used only for vector integrity), OPAQUE (`@serenity-kit/opaque`, P2-09),
  and any Ruvee format (P2-03).
- The heap checks rely on an undocumented internal and may need updating for a new build.

## Argon2id calibration benchmark (P2-02)

`src/calibration/` measures how long `crypto_pwhash` (Argon2id) takes with the proposed profile 1
and a few comparison configurations. It uses the same pinned libsodium.js as the checks above, the
same lockfile and the same version preflight. It is measurement tooling: it decides nothing, and
the [calibration report](../../docs/security/kdf-calibration.md) holds the results and their
limits. Inputs are synthetic.

### What it measures

The configurations come from a fixed registry in `src/calibration/core.mjs`; nothing else can be
passed to the library. Each cites its basis in the specification.

| Id           | Role                     | `memlimit` | `opslimit` | Argon2id parameters        |
| ------------ | ------------------------ | ---------- | ---------- | -------------------------- |
| `ref-19m-t2` | comparison (below floor) | 19 MiB     | 2          | v=0x13, m=19456, t=2, p=1  |
| `p1-64m-t3`  | baseline (profile 1)     | 64 MiB     | 3          | v=0x13, m=65536, t=3, p=1  |
| `c-64m-t4`   | candidate                | 64 MiB     | 4          | v=0x13, m=65536, t=4, p=1  |
| `c-128m-t3`  | candidate                | 128 MiB    | 3          | v=0x13, m=131072, t=3, p=1 |
| `p2-256m-t3` | reserved (profile 2)     | 256 MiB    | 3          | v=0x13, m=262144, t=3, p=1 |

All use a 32-byte output, a 16-byte salt and a 24-byte password, with no secret or associated
data. Before timing, each configuration's mapping is confirmed by libsodium's own
`crypto_pwhash_str` output (`$argon2id$v=19$m=…,t=…,p=1$`). The self-test checks one output
against noble.

Procedure, the same in Node and browsers:

- **One worker at a time.** A fresh worker (`worker_threads` in Node, a dedicated Web Worker in
  browsers) is created for each configuration and terminated afterwards, so no WebAssembly memory
  carries over. Configurations, engines and samples run strictly one after another.
- **Order:** the five configurations by increasing cost, then profile 1 again, to show drift from
  heat or power state during the run.
- **Per configuration:** 3 warm-up derivations (discarded), then 20 timed ones (`quick` mode: 1
  and 5). Only the `crypto_pwhash` call is timed, with `performance.now()` inside the worker.
  Reported: median, p95 (nearest rank; with 20 samples, the 19th), minimum, maximum, sample count,
  and failures. A failure stops that configuration and is recorded, never retried silently.
- **Initialisation** is measured separately: 10 workers in a row, each from creation to
  "libsodium ready", split into loading and evaluating the script and initialising libsodium.
  The first worker is reported apart from the other nine.
- **Memory**, only where it can be measured honestly:
  - Node: the **peak resident set size of the whole process** (`getrusage`), one child process per
    configuration, with the idle size of the same process for comparison.
  - Browsers: only the **WebAssembly linear memory size** after the run. That is the Argon2
    memory plus libsodium's own heap; it is **not** total peak memory, which browsers do not
    expose to the page. Total browser memory is not measured.

### Cancellation and cleanup

A derivation runs synchronously inside the worker and cannot be interrupted from within.

- **Cooperative cancel:** a `cancel` message is checked between derivations. The derivation in
  progress finishes, and the worker stops before the next one. Latency is up to one derivation.
- **Terminate:** `worker.terminate()` stops a derivation in progress and discards the worker and
  its WebAssembly memory. Nothing it computed is delivered. The benchmark checks that no message
  arrives after `terminate()`, and that a new worker then runs normally.
- The controller terminates every worker in a `finally` block, including after failures and
  timeouts. Output buffers and the password are wiped with `sodium.memzero` after use. JavaScript
  cannot guarantee that no copy remains, which is one reason all inputs are synthetic.
- The Node runner starts one child process per task, waits for it, and records each child's
  process id. On a timeout it kills only that child.

### V-15 and argument checks

Every library call goes through a guard in `core.mjs`, which throws before calling the library:

- `crypto_pwhash`: only registry configurations, `memlimit` in whole KiB and at most 256 MiB,
  output exactly 32 bytes, salt exactly 16 bytes, password 1 to 4,096 bytes. libsodium itself
  would round `memlimit` down silently and has no ceiling.
- `crypto_kdf_derive_from_key` (one 32-byte subkey per configuration, timed separately): subkey
  length exactly 32, key 32 bytes, an 8-character printable-ASCII context, id up to 2³¹ − 1.

The benchmark never calls `crypto_kdf_derive_from_key` with an invalid length. This guard is the
benchmark's own check. **It does not fix V-15**, which remains an open production integration
issue in libsodium.js 0.8.4 (fixed upstream on master, not released). The dependencies were not
changed. `LB-KDF-SUBKEY-LENGTH-STALE-MEMORY` above keeps tracking the library's behavior.

### Commands

From `tools/crypto-validation/`, after `npm ci`:

```sh
npm run calibration:selftest     # fast check of the tooling (also in CI); measures nothing
npm run calibration:node         # Node; writes results/calibration/node-<time>.json
npm run calibration:browsers     # Playwright browsers; writes results/calibration/browsers-<time>.json
npm run calibration:serve        # local page on http://127.0.0.1:8787/ for manual runs
node src/calibration/summarize.mjs   # Markdown tables from every result file, with an output-consistency check
```

- `MODE=quick` runs 1 warm-up and 5 samples instead of 3 and 20.
- `BROWSERS=chromium,firefox,webkit,chrome` (default) selects engines. `chrome` is the installed
  Google Chrome with a temporary profile.
- Playwright WebKit is a WebKit build, **not Safari**, even though its user-agent string says
  "Safari". Playwright Firefox is a patched build, not stock Firefox.
- Results stay in `results/` (ignored by git).

Measurements are only comparable on the same device under similar conditions. Before a run, plug
the device in, close other applications, and note the power and load state. CI runs the
self-test only, because timings on a shared runner would mean nothing.

### Manual runs: Safari and other devices

The page works in any browser with Web Workers and WebAssembly. It shows a results table and the
full JSON, and sends the JSON back to the computer serving it (saved in
`results/calibration/manual/`). Partial results survive a crash or reload of the tab, in
`localStorage`.

**Safari on a Mac** (no Safari settings, no "Allow Remote Automation", no OS changes):

1. `npm run calibration:serve` on that Mac.
2. Type `http://127.0.0.1:8787/` into Safari.
3. Enter the device, macOS and Safari versions and the power state in "Device and browser", keep
   Standard mode, and press Start. Leave the tab in the foreground for about two minutes.
4. When "Saved on the computer as …" appears, run `node src/calibration/summarize.mjs`.

**Android phone over USB**, which needs no network access: the phone reaches the computer's
loopback port through `adb`.

1. On the phone, enable USB debugging (the owner's choice; it changes a phone setting).
2. Connect it, then on the computer: `adb reverse tcp:8787 tcp:8787` and
   `npm run calibration:serve`.
3. Open `http://127.0.0.1:8787/` in Chrome on the phone and proceed as in step 3 above.
4. Afterwards, `adb reverse --remove tcp:8787`.

**iPhone, or any device without USB forwarding.** This needs the page on the local network, so
it exposes the server to that network while it runs. Decide this deliberately, and only on a
network you trust:

1. Find the computer's address on that network (for example `ipconfig getifaddr en0` on macOS).
2. `HOST=<that address> npm run calibration:serve`. The server refuses `0.0.0.0` and binds only
   that address. macOS may ask whether to allow incoming connections.
3. Open `http://<that address>:8787/` on the device and run it as above.
4. Stop the server with Ctrl+C as soon as the results are saved.

Over a plain-HTTP network address the page is not a secure context, so it is not cross-origin
isolated and its timers may be coarser; both are recorded in the results. Every browser on iOS
uses WebKit, so an iPhone run covers Safari's engine whichever browser is used.

Protocol for reference devices: battery above 50% and charging, Low Power or battery saver mode
noted (off if possible), other apps closed, screen on. Run Standard mode twice, a few minutes
apart, and keep both results. If a configuration fails (for example, the 256 MiB profile 2 runs
out of memory), that is a result: record it.
